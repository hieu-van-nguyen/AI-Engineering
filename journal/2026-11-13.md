# Day 2: async HTTP — concurrency limits and retries

- Time spent:
- What I did:
  - Wrote `m1-foundations/fetch_many.py`: 20 URLs fetched with `httpx.AsyncClient`, concurrency capped by `asyncio.Semaphore`, run through `asyncio.gather(..., return_exceptions=True)`, with a summary (successes, failures, total time, average per request). It runs its own small local server (0.5 s delay, some URLs return 500 on purpose), so no outside site gets hit.
  - Ran it with semaphore limits 1 / 5 / 20: 10.31 s / 2.10 s / 0.58 s. Recorded in `notes/async.md`.
  - Added a simple retry (2 attempts, short delay) to `fetch_one.py` and `fetch_many.py`. Only timeouts, connection errors and 5xx are retried; a 4xx fails right away.
- What broke / what confused me:
  - A plain `python -m http.server` answers almost instantly, so the semaphore limit barely changes the timing. An artificial delay on the server side was needed to see the difference.
  - Where to sleep during a retry: sleeping while holding the semaphore wastes a slot, so each attempt takes the semaphore on its own and the delay happens outside it.
- What I learned (1–3 bullets):
  - The semaphore doesn't make a single request faster (each one still takes ~0.5 s); it controls how many wait at once, so total ≈ ceil(N / limit) × latency.
  - `return_exceptions=True` puts exceptions into the result list instead of cancelling the rest of the batch; check `isinstance(result, BaseException)` to split successes from failures.
  - Retry only errors that might go away (timeouts, connection errors, 5xx). Retries add an extra "wave" to the total time.
